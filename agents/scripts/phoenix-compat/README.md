# Phoenix 5.0 / HBase 2.0 compatibility build

This is a DBX compatibility rebuild, **not an Apache release**. It changes the
official Phoenix 5.0.0-HBase-2.0 source's Shade plugin from 2.4.3 to 3.0.0, then
recompiles the Phoenix reactor. It does not patch JVM class bytes or downgrade
the DBX Java runtime. The DBX external-classpath isolation fix remains required.

## Build and approve

Use Zulu JDK `1.8.0_512-b09` (`JAVA_HOME`), Python 3 and approximately 2 GiB of
temporary space. Maven 3.9.9 and the source archive are acquired by the script
with pinned checksums. A fresh output directory is required:

```sh
python3 -m unittest discover -s agents/scripts/phoenix-compat -p 'test_*.py'
python3 agents/scripts/phoenix-compat/build.py build --work /absolute/new/build-directory
```

The private Maven repository is populated from `repository-lock.json`. Every
JAR/POM is SHA-256 pinned; the two version-range metadata documents are frozen.
Maven then runs **offline**, so a new transitive dependency or changed historical
range cannot silently enter the build. The lock is a complete observed build
repository, not a claim that every entry is minimally necessary. No Phoenix
main binary may appear in the lock; its published tests JAR is a build input.

`--repository-seed`, `--source-archive`, and `--maven-archive` may point at retained
verified inputs to avoid downloading them again. Inputs are copied, hash-checked
and never modified. Failed downloads never become approved repository files.

The release build checks its output against the compiled runtime catalog. A
different archive fails. `--candidate` is only for reviewing a new version; it
does not update the catalog and is never used by the release workflow. Changes
require review of source, dependency lock, package content and runtime tests,
then a **new** identity and catalog approval; do not overwrite an existing release.

## Portable package

The package contains `compatibility.json`, one synthetic DBX bundle manifest,
the rebuilt Phoenix JAR, unchanged ZooKeeper 3.4.10, provenance and extracted
LICENSE/NOTICE files. `app.dbx.compat:phoenix-hbase-2.0:5.0.0-dbx.1` is an internal
bundle identity, not a Maven Central coordinate. It is installed without changing
the JDBC plugin. The backend validates the catalog hash and each JAR before
activating the bundle. Online and local-file installation consume identical bytes.

Canonicalization sorts ZIP entries and uses stored entries with a fixed 1980
timestamp (larger files, independent of zlib versions). It removes only the outer
Phoenix manifest's `Built-By`, `Build-Jdk`, `Created-By` and comments in Phoenix
`pom.properties`. The `mrapp-generated-classpath` file generated by Phoenix's
`generate-test-resources` phase contains the build machine's absolute Maven/JDK
paths; its dependency order is retained with locked Maven-relative paths. No
Phoenix source or packaged client class references that resource name. Every
class byte is compared before and after. Signed outer
JARs are rejected; signatures are never silently invalidated. Dependencies'
license and notice content remains unchanged. JVM verification and actual
connection tests are still required; metadata normalization is not a test suite.

`package --phoenix ... --zookeeper ... --output ...` packages an existing input
for review. That command is **not evidence of a fresh source build**.

## Release dependency and validation limits

The manual `Phoenix compatibility runtime` workflow defaults to build-only.
Publishing requires an explicit input, the upstream default branch and release
write permission. The catalog URL is an intended versioned upstream release
location; adding it to source does not prove the release exists. Test the remote
asset and its checksum after maintainers actually publish it.

The historical source build skips Phoenix's full test suite, checkstyle, RAT and
Javadoc. Its Java21 read/query/reconnect tests and DBX desktop verification are
separate. The locked javax.el version differs from the historical Apache binary,
and Shade changes SPI resource relocation. Do not promise arbitrary HBase APIs,
DDL/writes, Windows, or all Java21 functionality without their own tests.
