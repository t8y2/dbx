## Data and Backup

<Accordions>
  <Accordion title="Where is my connection configuration stored?">
    DBX Desktop stores connections, saved credentials, SSH tunnel profiles, query history, and app settings in a single SQLite database file `dbx.db` inside the DBX data directory:

    - **Windows (installer):** `C:\Users\<user>\AppData\Roaming\com.dbx.app\dbx.db`
    - **Windows (portable ZIP):** `<DBX.exe folder>\data\dbx.db`
    - **macOS:** `~/Library/Application Support/com.dbx.app/dbx.db`
    - **Linux:** `~/.local/share/com.dbx.app/dbx.db`

    SSH host keys are kept in `known_hosts` in the same directory, so DBX never touches `~/.ssh`. Depending on write activity, `dbx.db-wal` and `dbx.db-shm` checkpoint files may sit next to the database.

    Older DBX releases kept connections in `connections.json` and `secrets.json`. These files are migrated into `dbx.db` automatically on startup and the originals are renamed to `*.bak`.

    To move connections to another machine, use encrypted [Config Export/Import](/en/docs/config-export) instead of copying files. For a manual backup, quit DBX first, then copy the whole data directory, or at least `dbx.db` together with the `-wal` and `-shm` files.
  </Accordion>
  <Accordion title="Can I keep the data next to the executable, or use a custom data directory?">
    Yes. There are two supported ways:

    - **Windows portable ZIP:** the `DBX_<version>_<arch>-portable.zip` from the release page ships with a `portable.dbx` marker file. Extract it anywhere and run it; all data is stored in the `data` folder beside `DBX.exe`. On first launch, if the portable folder is still empty and older data exists in `AppData`, it is imported automatically once.
    - **`DBX_DATA_DIR` environment variable:** works on every platform and for both installer and portable builds, and takes the highest priority. Point it at any folder. The new directory starts empty, so migrate with Config Export/Import, or copy `dbx.db` while DBX is not running.

    The `portable.dbx` marker only works on Windows, and it is ignored when `uninstall.exe` sits next to the executable (installed builds). There is no in-app setting for the data directory.
  </Accordion>
  <p>See the [Data Security Upgrade and Migration guide](/en/docs/data-security-migration) before upgrading an existing installation.</p>
</Accordions>

## Linux Window Flickering or Missing Content

The Linux main window draws a rounded, shadowed floating frame on GNOME in a Wayland session when a compositing manager is running. GNOME on X11 ("GNOME on Xorg") and other desktops (KDE, XFCE, Cinnamon, ...) use an opaque background by default to avoid transparent-window compositing problems with some graphics driver and WebKitGTK combinations. Neither mode disables GPU acceleration or changes the Wayland/X11 backend.

If the window flickers, turn off **Settings → Appearance → Window transparency**, apply the change, then fully quit DBX (including its tray process) and restart. The switch is on by default and follows the desktop detection rules.

Environment overrides take priority over the setting. To force the floating frame on X11 or another desktop:

```bash
DBX_LINUX_FLOATING_FRAME=1 dbx
```

To force the opaque window on GNOME Wayland, for example if you see flickering, missing content or redraws only after resizing, quit DBX completely, including its tray process, and restart with `DBX_LINUX_FLOATING_FRAME=0 dbx`. The frame is never used without a compositing manager. For AppImage installations, replace `dbx` with the actual AppImage path.

If the default opaque window still has problems, include the DBX version, installation format, KDE/Plasma version, Wayland/X11 session type, graphics hardware and driver details, and system WebKitGTK version in your report.

## Garbled PostgreSQL / openGauss text

For a database declared as `LATIN1` whose legacy text actually contains GB18030 bytes, enter the following in **Edit connection → Connection → URL parameters**:

```text
clientEncoding=GB18030&serverEncoding=ISO-8859-1
```

Save and reconnect. The native driver converts query results, SQL and bound parameters, including table editing, text arrays, JSON, metadata and row-based exports. This does not change the database encoding or existing data. `clientEncoding` also accepts `GBK` and `UTF-8`; `serverEncoding` accepts `LATIN1`. Both parameters are required together.

Use these parameters only when the declared database encoding differs from its text bytes. The server must report `server_encoding=LATIN1` and `standard_conforming_strings=on`. On reads, values that cannot be converted retain their original text and produce a query warning; valid values still decode normally. Byte-truncated masked values, such as half a multibyte character followed by asterisks, do not abort the whole query and are never replaced with NULL or replacement characters. Writes still reject characters that the selected encoding cannot represent. Connections without these parameters use normal PostgreSQL encoding conversion.

COPY imports support DBX's default text format; transfers use the row-based INSERT path. Use row-based import/export for raw COPY output or other COPY formats.

## What is the "Notes file" connection setting?

The **Notes file** setting (config key `docs_notes_path`) is where the [Database documentation](/en/docs/database-docs) feature stores its notes. You'll find it in the **Advanced** section of the connection form.

- Leave it empty and notes live in the DBX app data directory, one file per connection, with no setup.
- Point it at a file in your repository (for example `docs/dbx-docs.json`) to commit table and column notes with your code and review schema documentation in pull requests.
- The notes themselves are written in the viewer that opens when you right-click a table in the object browser and choose **Documentation**. They support Markdown and colour-coded groups, autosave, and the AI assistant reads the same file as descriptions for the matching tables and columns.

See [Database documentation](/en/docs/database-docs) for the file format, warning behaviour, and DBML export.
