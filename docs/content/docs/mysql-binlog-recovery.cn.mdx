此工作台仅在桌面端提供，目前属于实验功能，不会连接数据库或执行恢复 SQL。
请先完成独立审核、备份及恢复演练，不要将实验验证结果视为生产验收。

## 打开与查看

1. 在桌面工具栏选择 **更多 → MySQL Binlog 恢复**。
2. 点击 **导入 binlog**，选择本地 MySQL 8.0 binlog 文件。
3. 按数据库、表、GTID、本地时间或物理位置筛选。结果始终保留整笔事务，
   不会因为筛选某张表就丢弃同一事务内其他表的数据。
4. 点击事务查看已记录的前后值。位置和整数使用精确字符串，字节数据以十六进制
   展示；未记录与 SQL NULL 分开显示。缺少符号位时显示原始位模式，不冒充确定数值。

当前要求 ROW + FULL 行镜像以及丰富的表元数据（通常需要
`binlog_row_metadata=FULL`）。缺少历史列名、数值符号位或可靠主键信息会拒绝生成。
现在修改服务器配置，不会补齐过去文件中缺失的信息。

## 历史结构依据

选择历史结构 JSON，并明确确认其历史依据。不能仅因为列数相同，就将当前表结构
当作历史结构。清单需要绑定完整文件的 SHA256、有效位置范围、历史来源、精确的有序
列元数据及非空主键。仓库中的 `examples/mysql-binlog-probe/README.md` 说明了格式，
`tests/live_mysql.py` 提供在隔离实例中、操作发生前采集结构的可复现实例。

结构清单外层示例（`tables` 必须补充真实核实的定义，不可直接猜测使用）：

```json
{
  "version": 1,
  "binlog_sha256": "<导入文件完整内容的 SHA256>",
  "valid_from": 156,
  "valid_to": 2173,
  "provenance": "<已核实的历史结构来源>",
  "historical": true,
  "tables": []
}
```

## 预览和导出

整笔选择事务后点击 **生成 SQL 预览**。校验失败不会生成可导出的 SQL。
若后续未选事务修改了已选事务涉及的表，会保守拒绝；请纳入相关事务或独立分析依赖。
修改选择、筛选或历史结构后，旧 SQL 自动失效。

**导出 .sql** 只写入新文件，不覆盖已有文件或符号链接。工作台没有执行按钮。

恢复脚本采用随机名称的 INVOKER 权限存储过程，检查目标结构、完整预期后镜像，
并在冲突时回滚当前逆向事务。**每笔事务分别提交，后续失败不会撤销先前已提交的恢复**，
不要直接重跑失败脚本。

人工执行需要全新的专用自动提交会话、例程权限、完整元数据可见性，并在首个错误时停止。
创建辅助例程会隐式提交，因此不要复用已有工作事务的会话。失败 CALL 可能留下辅助例程，
需要人工清理。必须独立确认不存在触发器或任何方向的外键；权限过滤后的元数据计数为零
并不能证明不存在这些对象。

## 支持范围与限制

- 已验证整型、二进制／文本、精确 DECIMAL、普通完整 JSON，以及带微秒的现代
  DATETIME／TIMESTAMP／TIME。
- 暂不支持 DATE、普通浮点列、ENUM／SET、空间类型、生成列、零值或无效时间、
  不透明 JSON 类型、部分 JSON、DDL 回滚、压缩事务、触发器及外键。
- 解析子进程限制为 60 秒、采样 RSS 512 MiB，并支持显式取消；采样不是操作系统硬内存上限。
- 文件最大 512 MiB、单事件最大 16 MiB，恢复最多物化 50,000 行／10,000 笔事务，
  表映射 ID 最多 128 个。每页最多 100 笔事务或行变化，响应最大 8 MiB。

MySQL 8.0.27 隔离验收覆盖了逐字段恢复及冲突处理，但不代表生产验收、完整恶意输入安全
或 Windows／Linux 分发验证已完成。
