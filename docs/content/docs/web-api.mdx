## Base URL

By default, DBX Web listens on port `4224`:

```text
http://localhost:4224
```

When deployed behind a reverse-proxy subpath, set `DBX_PUBLIC_BASE_PATH` and prefix every route. For example, with `/dbx`:

```text
https://example.com/dbx/api/auth/check
```

All API routes are under `/api`.

## Authentication

Protected routes require a session cookie named `dbx_session`.

### Check Auth State

```http
GET /api/auth/check
```

Example response (Password auth):

```json
{
  "authenticated": false,
  "required": true,
  "setup_required": false
}
```

Example response (with OIDC configured):

```json
{
  "authenticated": false,
  "required": true,
  "setup_required": false,
  "oidc": {
    "enabled": true,
    "button_label": "Sign in with SSO",
    "password_disabled": false
  }
}
```

Example response (when authenticated):

```json
{
  "authenticated": true,
  "required": true,
  "setup_required": false,
  "user": {
    "sub": "user-12345",
    "email": "user@example.com",
    "name": "Jane Doe",
    "role": "Admin",
    "method": "oidc"
  }
}
```

| Field | Meaning |
| --- | --- |
| `required` | Authentication protection is active (via password or OIDC) |
| `setup_required` | First-run password setup is still needed (only `true` when neither password nor OIDC is configured) |
| `authenticated` | Current request already has a valid session |
| `oidc` | Present when OIDC SSO is enabled, containing UI metadata (`button_label`, `password_disabled`) |
| `user` | Present when authenticated, providing user profile info and login `method` (`password` or `oidc`) |

### First-Run Setup

```http
POST /api/auth/setup
Content-Type: application/json

{
  "password": "your-password"
}
```

<Callout type="info">First-run setup is only active when both password hash and OIDC configuration are absent (`setup_required: true`). When OIDC is configured, first-run setup is bypassed in favor of IdP login. To use password auth alongside OIDC, supply `DBX_PASSWORD` in your environment.</Callout>

### Login

```http
POST /api/auth/login
Content-Type: application/json

{
  "password": "your-password"
}
```

On success, the response sets `Set-Cookie: dbx_session=...`. Reuse that cookie on later requests.

Five consecutive login failures trigger an approximately 60-second lockout. Sessions live in the current Web process and require login again after restart. The cookie is `HttpOnly`, uses `SameSite=Lax`, and follows `DBX_PUBLIC_BASE_PATH` for its path.

### OIDC / Single Sign-On (SSO)

DBX Web supports OpenID Connect (OIDC) with Authorization Code Flow + PKCE (RFC 7636), automatic IdP discovery, and CEL admission control.

#### 1. Initiate OIDC Login

```http
GET /api/auth/oidc/start
```

Redirects the browser to the Identity Provider (IdP) authorization endpoint with PKCE code challenge and CSRF state parameter.

#### 2. OIDC Callback

```http
GET /api/auth/oidc/callback?code=...&state=...
```

The IdP redirects back to this callback endpoint. DBX exchanges the authorization code for tokens, verifies the `id_token` signature against IdP JWKS, checks admission policies, creates a session cookie, and redirects the user to the root application (`/`).

**Redirect URI configuration on IdP:**
```text
<DBX_PUBLIC_URL>/api/auth/oidc/callback
```

#### 3. CEL Admission Gatekeeper & Role Mapping

<Callout type="warn">**Current Limitation (Multi-User & Multi-Role Support)**: CEL admission gatekeeping currently controls whether a user is allowed to log in (admission pass/fail). However, full multi-user credential isolation and fine-grained multi-role RBAC enforcement are still under development and tracked in [Issue #8627](https://github.com/t8y2/dbx/issues/8627). At present, all admitted users share the same instance workspace and connections. Returning custom role strings from CEL serves as schema preparation for upcoming RBAC releases.</Callout>

DBX Web uses [Google Common Expression Language (CEL)](https://github.com/google/cel-spec) via `DBX_OIDC_ADMISSION_EXPR` to control admission and assign user roles based on IdP token claims.

**Context Variable:**
- `claims`: Map of merged claims from `id_token` and `userinfo` (e.g. `claims.sub`, `claims.email`, `claims.groups`, `claims.roles`, `claims.email_verified`).

**Evaluation Rules & Return Types:**
- **`bool`**:
  - `true`: Admitted with default role `"Admin"`.
  - `false`: Rejected with HTTP 403 (`access_denied`).
- **`string`**:
  - Non-empty string: Admitted with the returned string as the user's role (e.g. `"Admin"`, `"Developer"`, `"Viewer"`).
  - Empty string `""` or `null`: Rejected with HTTP 403 (`access_denied`).

**Filter Execution Pipeline:**
1. `DBX_OIDC_ALLOWED_DOMAINS`: If set, validates that `claims.email` ends with one of the allowed domains.
2. `DBX_OIDC_ADMISSION_EXPR`: If set, evaluates the CEL expression against `claims`.
3. If no admission expression is set, any valid authenticated user is admitted with role `"Admin"`.

**Common Examples:**
```bash
# Allow only users in the 'admin' group
DBX_OIDC_ADMISSION_EXPR='"admin" in claims.groups'

# Require verified email address
DBX_OIDC_ADMISSION_EXPR='claims.email_verified == true'

# Allow specific department with email domain check
DBX_OIDC_ADMISSION_EXPR='claims.email.endsWith("@company.com") && ("infra" in claims.departments)'

# Dynamic Role Mapping based on group membership
DBX_OIDC_ADMISSION_EXPR='"infra-admins" in claims.groups ? "Admin" : "devs" in claims.groups ? "Developer" : ""'
```

### Environment Variables

#### Core & Web

| Variable | Purpose |
| --- | --- |
| `DBX_PASSWORD` | Set an initial password at container startup |
| `DBX_DISABLE_PASSWORD=1` | Disable password protection entirely |
| `DBX_PORT` | Change the listen port (default `4224`) |
| `DBX_DATA_DIR` | Data directory containing `dbx.db` |
| `DBX_PUBLIC_BASE_PATH` | Serve DBX under a subpath such as `/dbx` |
| `DBX_MAX_UPLOAD_MB` | Override the general request and uploaded-file limit; default 1024 MB. Multipart routes reserve fixed protocol overhead (set at least `4096` for a 4 GiB file) |
| `DBX_AGENT_DIR` | Override the Web Agent/driver directory; defaults to `agents` under the data directory |
| `DBX_STATIC_DIR` | Override the Web static asset directory |
| `DBX_WEB_COOKIE_SECURE=1` | Explicitly enforce `Secure` flag on session cookies (useful behind TLS reverse proxies) |
| `RUST_LOG` | Configure Rust backend log filtering; the default is `dbx_web=info,tower_http=info` |
| `RUST_BACKTRACE=1` | Include Rust backtraces when an error reports one |

#### OIDC / SSO Configuration

| Variable | Required | Purpose |
| --- | :---: | --- |
| `DBX_PUBLIC_URL` | **Yes** (when OIDC enabled) | Public base URL of DBX (e.g. `https://dbx.example.com`, no trailing slash) |
| `DBX_OIDC_ISSUER` | **Yes** (enables OIDC) | OpenID Provider Issuer URL containing `.well-known/openid-configuration` |
| `DBX_OIDC_CLIENT_ID` | **Yes** | Client ID registered with the IdP |
| `DBX_OIDC_CLIENT_SECRET` | No | Client Secret (for confidential clients) |
| `DBX_OIDC_SCOPES` | No | Space-separated OAuth scopes (default: `openid profile email`) |
| `DBX_OIDC_BUTTON_LABEL` | No | Custom text on the SSO button (default: `Sign in with SSO`) |
| `DBX_OIDC_DISABLE_PASSWORD` | No | Set `true` to hide the password login form and enforce SSO only |
| `DBX_OIDC_ALLOWED_DOMAINS` | No | Comma-separated list of allowed email domains (e.g. `example.com,company.org`) |
| `DBX_OIDC_ADMISSION_EXPR` | No | [CEL](https://github.com/google/cel-spec) expression for claims admission/RBAC (e.g. `'admin' in claims.groups`) |
| `DBX_COOKIE_SECURE` | No | Override cookie `Secure` flag (auto-enabled when `DBX_PUBLIC_URL` starts with `https://`) |

## Logging and Troubleshooting

DBX Web reads the standard `RUST_LOG` filter when it starts. For a focused diagnostic run, increase the Web and HTTP middleware targets without enabling every dependency:

```bash
RUST_LOG=dbx_web=debug,tower_http=info ./dbx
```

Set `RUST_BACKTRACE=1` as well when the error includes a Rust backtrace. If the problem is inside another DBX crate, add its target to the same filter, such as `dbx_core`, `dbx_drivers`, `dbx_sql`, `dbx_plugin_runtime`, `dbx_ai_provider`, or `dbx_platform`. `RUST_LOG=debug` enables a much broader and noisier filter. Logs are written to the process output; redirect that output when you need to save a diagnostic file.

## Request Format

- Field naming follows each Rust request type. Some bodies use `camelCase`, while connection configuration still contains `snake_case`; do not apply one naming convention to the whole API.
- `GET` query parameters commonly use `snake_case`, such as `connection_id`, but the current route implementation remains authoritative.
- Errors usually return JSON with an `error` field and an HTTP status code.
- Long-running export, import, transfer, SQL-file, and AI operations commonly use a start request plus SSE progress and cancel/download routes rather than one synchronous response.

Only the data-grid extractor currently exposes a tested, scoped OpenAPI document at `/api/query/data-grid-extractor-openapi.json`. It does not cover the complete DBX Web API or version the other routes.

## Connection APIs

### List Connections

```http
GET /api/connection/list
Cookie: dbx_session=...
```

Returns saved connection profiles. Secrets such as passwords are stored separately from the returned JSON.

### Save Connections

Connections are upserted by `id`: connections the request does not mention are left untouched, so several
clients can share one server without deleting each other's profiles. Deletions are explicit through the
optional `removedIds` array.

```http
POST /api/connection/save
Content-Type: application/json
Cookie: dbx_session=...

{
  "configs": [
    {
      "name": "local-mysql",
      "db_type": "mysql",
      "host": "127.0.0.1",
      "port": 3306,
      "username": "root",
      "database": "app"
    }
  ],
  "removedIds": ["connection-to-delete"]
}
```

### Test Connection

```http
POST /api/connection/test
Content-Type: application/json

{
  "config": {
    "name": "temp",
    "db_type": "mysql",
    "host": "127.0.0.1",
    "port": 3306,
    "username": "root",
    "database": "app"
  }
}
```

### Connect

Most data APIs expect the target connection to be active first.

```http

    "db_type": "mysql",
    "host": "127.0.0.1",
    "port": 3306,
    "username": "root",
```

## SQL Query APIs

### Execute One Statement

```http
POST /api/query/execute
Content-Type: application/json

{
  "connectionId": "connection-id",
  "database": "app",
  "sql": "select id, name from users limit 10"
}
```

Example response shape:

```json
{
  "columns": ["id", "name"],
  "rows": [[1, "Ada"], [2, "Lin"]]
}
```

Related routes:

| Route | Purpose |
| --- | --- |
| `/api/query/execute-multi` | Execute multiple result sets in one request |
| `/api/query/execute-batch` | Execute a list of statements |
| `/api/query/cancel` | Cancel a running query |
| `/api/query/build-table-select-sql` | Build a table browse query |

## MCP and CLI Integration

For automation, these packages are usually easier to maintain than calling the Web API directly:

- MCP: [@dbx-app/mcp-server](/en/docs/mcp)
- CLI: [@dbx-app/cli](/en/docs/cli)

When MCP runs against a deployed Web instance, set:

```json
{
  "env": {
    "DBX_WEB_URL": "http://localhost:4224",
    "DBX_WEB_PASSWORD": "your-password"
  }
}
```

The MCP server handles login and session cookies for you.

CLI supports the same `DBX_WEB_URL` and `DBX_WEB_PASSWORD` variables. Both integrations reuse server-side connections, drivers, read-only protection, production protection, and database privileges, making them easier to maintain across DBX upgrades than copied internal route payloads.

## Writes, Safety, and File Boundaries

- API authentication proves only that the request belongs to a logged-in session; it does not replace database privileges
- Query, import, and transfer paths continue to enforce connection read-only protection, while production and SQL-risk policy apply in their corresponding core paths
- Browser-selected table-import and SQL files are uploaded into server temporary storage, not read from arbitrary client paths
- Web exports create a temporary server file, return it through a download route, and then clean it up
- Reverse proxies should preserve cookies and SSE streaming, allow appropriate long-running timeouts, and limit public exposure
