# DBX for Codex

[简体中文](README.zh-CN.md)

This plugin bundles the native `dbx-codex` MCP gateway and `dbx-web` with its embedded frontend. Codex starts the local workbench when it connects to the plugin. The DBX desktop app, Node.js, Rust and Docker are not runtime requirements.

The workbench uses the existing DBX Web UI and database execution backend. Features that normally require external database servers, driver agents, system libraries or cloud services retain those requirements; packaging does not turn them into built-in services.

## Install a native artifact

Choose the archive matching your operating system and CPU, verify its SHA-256 against `SHA256SUMS`, and extract it into a permanent directory. It contains `plugins/dbx` and `.agents/plugins/marketplace.json` (include hidden files when moving it).

```sh
codex plugin marketplace add /absolute/path/to/extracted-directory
codex plugin add dbx@dbx-local
```

Enable DBX in Codex if prompted. Existing chats may need a fresh MCP connection before its tools appear. Ask Codex to open DBX: `dbx_codex_open` returns the URL to open in the Codex browser panel. On first use, set a workbench password and complete the existing security migration. Add connections in the workbench and configure MCP permissions there.

`dbx_codex_open_table` opens a table. `dbx_codex_execute_and_show` executes through the existing MCP batch executor and links to those exact original results. Opening the link never reruns SQL. Links expire after five minutes or a service restart; expired write results must not be regenerated by repeating a write.

Closing a panel or disconnecting an MCP client leaves the shared service running. `dbx_codex_status` reports its identity and tracked activity; activity tracking is incomplete, so zero tracked tasks does not prove it is idle. `dbx_codex_stop` refuses unless `confirm_interrupt=true` explicitly authorizes interrupting **all** clients and ongoing work. Persistent data remains after stopping or uninstalling.

## Data and security

The default data directory is the OS local data directory plus `com.dbx.codex`: `~/Library/Application Support/com.dbx.codex` on macOS, `$XDG_DATA_HOME/com.dbx.codex` (normally `~/.local/share/com.dbx.codex`) on Linux, and `%LOCALAPPDATA%\com.dbx.codex` on Windows. It is separate from DBX desktop data. To use another directory, provide the absolute `DBX_CODEX_DATA_DIR` environment variable to Codex before it starts the plugin. Back up the entire directory, including its encryption key, rather than copying only connection records.

The service binds only to `127.0.0.1` on an ephemeral port. Web requests use the existing password/session flow; database MCP is gated until setup and migration complete. A private local token protects MCP and lifecycle endpoints. Host/Origin checks prevent foreign browser origins from driving the workbench. Runtime files use private Unix permissions or protected Windows ACLs. Do not expose the listener through a reverse proxy or share the data directory with untrusted local users. `workbench.log` in the data directory contains backend diagnostics; review it before sharing.

## Build and verify

### Workbench capabilities

| Capability | Codex behavior |
| --- | --- |
| Connections, SQL editor/execution/cancellation, history, permissions, table paging/editing | Existing Web UI and HTTP/core implementation; same persisted connections as MCP |
| MCP table navigation and original query results | Codex-specific opaque intents; no SQL replay |
| Import/export, SQL uploads/downloads, SQLite paths | Existing Web flows; paths refer to the local backend host, browser downloads use the browser |
| Redis/MongoDB and other database types | Existing Web adapters; actual servers/credentials remain required |
| Driver manager and DBX plugin center | Existing Web capabilities; driver agents/JRE/system dependencies are installed separately when needed |
| Desktop filesystem watchers/external SQL folder editing, desktop deep links, native updater | Existing Web limitations; desktop-only API calls report unavailability. Update this plugin through Codex/native artifacts |
| DBX third-party plugin native UI/storage/media access | Existing Web backend does not provide desktop-only APIs; individual plugin compatibility must be checked |

The plugin does not broaden the existing Web backend's desktop-only capabilities. SQLite and native plugin lifecycle are covered by the packaged end-to-end verifier; the repository's Web, MCP and frontend suites cover shared behavior. External database types and third-party plugins are not all live-tested by that verifier.

Build tools are needed only by developers. Follow the repository's native prerequisites, then use Node.js 24+, pnpm and Rust:

```sh
pnpm install --frozen-lockfile
pnpm --filter @dbx-app/mongo-shell build
pnpm build
cargo build --locked --release -p dbx-codex -p dbx-web --features dbx-web/codex-plugin
node scripts/package-codex-plugin.mjs --target aarch64-apple-darwin --binaries target/release --output target/codex-plugin/local
node --test scripts/package-codex-plugin.test.mjs
node scripts/verify-codex-plugin.mjs --plugin-dir target/codex-plugin/local/plugins/dbx
```

Replace the target with your native host target. The packager executes both programs, checks versions, verifies embedded assets and full default backend features, and refuses an existing output directory. `codex-plugin` embeds frontend assets even in debug builds; plain `embed-static` in debug mode is insufficient. The end-to-end verifier creates a disposable SQLite fixture, checks policy/result/lifetime/restart behavior, then stops its own service. `--keep-running` retains that test service for browser acceptance and prints its URL. Its fixture password is `DBX-native-acceptance-only-42!`; never use that password for real data.

The manually dispatched **Codex Plugin Native Artifacts** workflow builds/tests/packages macOS, Linux and Windows on both x64 and ARM64 native runners. It uploads archives and checksums, without publishing a release. The initial local acceptance covers macOS ARM64. Windows ACL tests cross-compile locally; other platforms need the native workflow to pass before distribution. Artifacts are unsigned development builds; official signing/release publication remains a maintainer decision.

This is a local Codex plugin marketplace, not a submission to the public OpenAI plugin directory. Plugin manifests follow the supported Codex compatibility layout documented in [OpenAI's plugin guide](https://developers.openai.com/plugins/build/plugins).
